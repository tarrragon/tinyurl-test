# loadtest

壓測在這個專案裡是伺服器能力評估：在手上這台練習用的機器上，量出系統大概能承受多少流量、瓶頸在哪一層，並在同一套情境下比較 Go 與 Laravel 兩個後端、以及不同的快取伺服器。它不是發布前要通過的門檻。這個資料夾放壓測腳本、測試資料的產生方式與每次的結果紀錄，目前只有需求，還沒有腳本。

## 壓測要回答的問題

1. **容量上限**：轉址路徑 `GET /{code}` 在固定的機器資源下，每秒能處理多少請求，以及超過多少之後延遲開始急升。
2. **瓶頸在哪一層**：到達上限時，先滿的是 Nginx、應用程式、快取、PostgreSQL 的連線數，還是點擊事件的寫入。
3. **兩個後端的差異**：同樣的資源、同樣的資料、同樣的情境下，Go 與 Laravel 的吞吐量、延遲與資源用量。
4. **快取選型的差異**：Valkey、Redis、Dragonfly 換掉之後轉址路徑的差異（見 [infra/cache/README.md](../infra/cache/README.md)）。
5. **保護機制有沒有作用**：Nginx 的限流有沒有擋下超量請求、一個後端掛掉時流量能不能轉到另一個、快取掛掉時能不能退回查資料庫。
6. **點擊數準不準**：壓測送出多少次轉址請求，後台統計就要記到多少次點擊，行銷報表依賴這個數字。

## 情境

每個情境寫成獨立的腳本，參數（目標速率、持續時間、短碼數量）由環境變數帶入。

| 情境           | 流量形狀                                                                 | 主要觀察                                         |
| -------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 轉址基準       | 只打 `GET /{code}`，短碼依熱門度分布（少數連結佔多數點擊），速率逐段升高 | 吞吐量開始持平與延遲開始急升的位置、快取命中率   |
| 爆紅連結       | 簡訊發送後的情形：同一個短碼在數秒內從零升到高峰                         | 單一快取 key 的負載、應用程式內快取的效果、錯誤率 |
| 混合流量       | 轉址、建立連結、建立發送、後台查詢依比例同時進行；階段七起加上模擬電商回報轉換的請求（含重送） | 建立連結、後台報表與轉換回報會不會拖慢轉址；轉換數比對 |
| 快取失效       | 快取清空後開始壓，或壓測途中停掉快取                                     | 退回查資料庫時的延遲與 PostgreSQL 連線數         |
| 限流驗證       | 單一來源超過限流門檻                                                     | 超量請求是否收到 `429` / `503`、其他來源不受影響 |
| 後端故障       | 壓測途中停掉 Go 或 Laravel 其中一個容器                                  | Nginx 是否把流量移到另一個後端、移轉期間的錯誤數 |
| 短碼掃描       | 大量隨機、不存在的短碼                                                   | 打到 PostgreSQL 的查詢數、Bloom filter 與限流的效果 |
| 長時間穩定     | 中等速率持續數小時                                                       | 記憶體是否持續成長、`click_events` 寫入是否積壓  |

混合流量的比例要依實際使用推估：一條連結建立一次、會被點擊很多次，所以轉址遠多於建立連結。比例在第一版需求確定時填入，不要沿用工具的預設值。

## 執行條件

- **送出請求的速率固定（open model）**：依每秒到達的請求數送，不依「固定人數、每人等回應後再送下一個」送。後者在服務變慢時自動降低送出的速率，會把延遲的問題藏起來，而簡訊點擊是不會因為服務變慢而減少的。
- **打短網域**：轉址情境的請求送到 `SHORT_DOMAIN`，Nginx 依主機名稱分流，所以請求要帶正確的 `Host` header；壓測工具解析不到 `s.localhost` 時，直接連 Nginx 的位址並手動設 `Host`。
- **不跟隨轉址**：壓測工具只量服務回 `302` 的時間，不要跟到目的地網站，否則量到的是外部網站。
- **分開與合併各量一次**：Go 與 Laravel 平常在同一個 upstream 輪流接請求。評估單一後端的能力時，換一份只放那個後端的 Nginx 設定再壓；兩個一起放時量的是整體能力，結果依 `X-Backend` 分開統計各自的延遲與錯誤。
- **公平比較**：比較 Go 與 Laravel、或比較快取時，容器的 CPU 與記憶體上限相同、資料相同、先暖機再計時，每組至少跑三次；壓測工具與受測服務不要搶同一台機器的 CPU。
- **測試資料**：事先建立固定數量的連結（數量與熱門度分布寫在腳本裡），每次壓測前重建，結果才能互相比較。
- **模擬轉換回報**：腳本不跟隨轉址，從 `302` 回應的 `Location` 取出 `tc` 參數再送轉換回報，所以測試資料的目標網址主機要列在 `CONVERSION_HOSTS` 裡。點擊分類規則的清單若包含 k6 的 User-Agent，壓測時要另外設成一般瀏覽器的 User-Agent，否則人為點擊都是 0。壓測機只有一個 IP 與 User-Agent，共用連結的不重複點擊每天每條連結只會是 1，這個數字在壓測下沒有意義。（階段七起）

## 要記錄的指標

- 每秒請求數、延遲的 p50 / p95 / p99、錯誤率（依狀態碼分開）。
- 各層資源：Nginx 與應用程式的 CPU 與記憶體、快取命中率、PostgreSQL 的連線數與慢查詢。
- 點擊數比對：送出的轉址請求數 vs 後台記到的點擊數。
- 每次結果存成檔案放在 `results/`，附上當次的 commit、後端、快取選項與機器資源。

## 評估結果怎麼讀

這裡跑的環境是本機或小型虛擬機上的 `docker compose`，不是商用等級的雲端，所以量到的數字只代表這台機器、這組容器資源上限下的能力。每份結果都要附上機器規格（CPU 核心數、記憶體、磁碟類型）與各容器的資源上限，數字才有意義。

每次評估要整理出的結論：

- **可承受的流量**：轉址在錯誤率仍為零、p99 延遲低於 200 ms（[docs/system-design.md](../docs/system-design.md) 的非功能需求）的前提下，每秒最多能處理多少請求；再和同一份文件〈容量估算〉的尖峰設計目標比較。這是這台機器的能力上限，不是目標值。
- **先到極限的是哪一層**：Nginx、應用程式、快取、PostgreSQL 連線數或點擊事件寫入。換到更大的機器時，這個順序比絕對數字更有參考價值。
- **換算成業務的量**：把每秒請求數換成行銷聽得懂的量，例如一次簡訊發送給多少人、多少比例的人在發送後幾分鐘內點擊，系統還接得住。
- **Go 與 Laravel、各快取選項的相對差異**：同一台機器上的比例（例如 Go 的吞吐量是 Laravel 的幾倍）可以參考，絕對值換一台機器就不同。

這個環境有兩個限制要寫在結果裡：

- **壓測工具和受測服務在同一台機器上**時，兩者搶同一批 CPU，量到的上限會偏低；有第二台機器時，把壓測工具移過去。
- **不能直接按比例推到雲端**：多開幾個應用程式實例不會讓容量等比增加，因為 PostgreSQL 與快取是所有實例共用的，實例越多，越快先撞到它們的上限。

## 工具（待決定）

| 工具   | 特點                                                                                     |
| ------ | ---------------------------------------------------------------------------------------- |
| k6     | 腳本用 JavaScript；支援固定到達速率與逐段升速的情境，結果可輸出成檔案或接 Grafana       |
| Vegeta | 命令列工具，固定速率送 HTTP 請求，適合單一路徑的轉址基準                                 |
| Locust | 腳本用 Python，適合模擬多步驟的使用者操作（登入後建立連結）                              |

建議先用 k6：上面的情境都需要固定到達速率，它的 `ramping-arrival-rate` 可以讓速率逐段升高，正好用來找可承受流量的上限。k6 有官方映像檔（`grafana/k6`），不需要另寫 Dockerfile。

## 預定的目錄結構

```text
loadtest/
├── scenarios/   # 每個情境一個腳本
├── seed/        # 產生測試連結的腳本
└── results/     # 每次壓測的結果紀錄
```
