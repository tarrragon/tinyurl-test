# 資料表與程式介面

這份文件定下第一版 migration 要建出的資料表（欄位、型別、約束、索引的名稱）、兩個後端共用的程式介面，以及 Go 與 Laravel 各自怎麼對應這些資料表。它是[開發順序](roadmap.md)〈階段一：定案與骨架〉的產物。

下面的 SQL 是規格：Laravel 的 migration 與 Go 的 Atlas migration 各自寫一套，兩套都要建出這份 SQL 描述的 schema，CI 比對兩套的結果（做法見 [infra/postgres](../infra/postgres/README.md)〈誰管 schema〉）。

## 資料表的共通約定

| 項目 | 約定 | 理由 |
| --- | --- | --- |
| 主鍵 | `bigint GENERATED BY DEFAULT AS IDENTITY` | PostgreSQL 建議的自動編號寫法；`BY DEFAULT` 讓測試資料可以指定 `id` |
| 約束與索引的名稱 | 一律在 SQL 裡寫明，例如 `links_code_key` | 兩個框架自動命名的規則不同（Laravel 的唯一索引叫 `links_code_unique`），不寫明的話 CI 的 schema 比對永遠不一致。程式也靠名稱判斷是哪一個約束被違反，見〈短碼重複的判斷〉 |
| 時間 | `timestamptz`；`created_at` 由資料庫的 `DEFAULT now()` 給值 | 建立時間由資料庫決定，兩個後端寫進去的值就沒有精度與時區的差別。API 輸出時再格式化成到秒的 UTC（見 [API 與路由規格](api.md)〈共通約定〉） |
| 列舉值 | `text` 加 `CHECK (... IN (...))`，不用 PostgreSQL 的 `ENUM` 型別 | `ENUM` 加值要 `ALTER TYPE`，刪值與改名做不到；`CHECK` 改一條約束就好 |
| 字串長度 | `text` 加 `CHECK (char_length(...) ...)` | 長度上限是業務規則，寫在約束裡改起來只動一條 |
| `updated_at` | 不設 | 沒有任何 API 或報表會讀它；Laravel 的 model 要明確關掉（見〈Laravel 的 model〉） |

**驗證兩邊都做**：後端程式先檢查欄位，不合規則時回 API 規格裡的錯誤碼；資料庫的約束是兩個後端共同的最後一道檢查，程式漏掉的錯誤值會在寫入時失敗，而不是存進去。點擊事件是例外，見〈click_events〉。

## 資料表

### teams

```sql
CREATE TABLE teams (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT teams_name_check CHECK (char_length(name) BETWEEN 1 AND 100),
  CONSTRAINT teams_name_key   UNIQUE (name)
);
```

團隊名稱不能重複：後台的使用者管理用名稱選團隊，兩個同名的團隊會讓管理者選錯。重複時 API 回 `409`、`team_name_taken`。

### users

```sql
CREATE TABLE users (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email         text        NOT NULL,
  password_hash text        NOT NULL,
  role          text        NOT NULL,
  team_id       bigint      REFERENCES teams (id),
  created_at    timestamptz NOT NULL DEFAULT now(),
  disabled_at   timestamptz,
  CONSTRAINT users_email_check CHECK (email = lower(email) AND char_length(email) <= 254),
  CONSTRAINT users_role_check  CHECK (role IN ('marketing', 'marketing_lead', 'engineer', 'admin')),
  CONSTRAINT users_team_check  CHECK (role NOT IN ('marketing', 'marketing_lead') OR team_id IS NOT NULL),
  CONSTRAINT users_email_key   UNIQUE (email)
);
CREATE INDEX users_team_id_idx ON users (team_id);
```

- **email 一律存小寫**：兩個後端在寫入與登入比對前都先轉成小寫，約束擋下沒轉的值。這樣 `Alice@example.com` 與 `alice@example.com` 是同一個帳號，唯一索引也不必用運算式索引。
- **`team_id` 可以是空的**：`engineer` 與 `admin` 不屬於任何行銷團隊。行銷的兩個角色一定要有團隊，因為他們看得到的連結範圍依團隊決定（見 [API 與路由規格](api.md)〈「範圍依角色」的意思〉），由 `users_team_check` 擋下沒有團隊的行銷帳號。這時 JWT 的 `team_id` claim 是 `null`。
- **`password_hash` 的格式**見 [登入與權限](auth-and-roles.md)〈密碼〉：兩個後端都要驗得過對方產生的雜湊值。

### links

```sql
CREATE TABLE links (
  id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  code         text        NOT NULL,
  original_url text        NOT NULL,
  channel      text        NOT NULL,
  campaign     text        NOT NULL,
  created_by   bigint      NOT NULL REFERENCES users (id),
  team_id      bigint      REFERENCES teams (id),
  created_at   timestamptz NOT NULL DEFAULT now(),
  expires_at   timestamptz NOT NULL,
  disabled_at  timestamptz,
  CONSTRAINT links_code_check     CHECK (code ~ '^[0-9A-Za-z]{6,7}$'),
  CONSTRAINT links_url_check      CHECK (char_length(original_url) <= 2048),
  CONSTRAINT links_channel_check  CHECK (channel IN ('sms', 'email', 'ad')),
  CONSTRAINT links_campaign_check CHECK (char_length(campaign) BETWEEN 1 AND 100),
  CONSTRAINT links_code_key       UNIQUE (code)
);
CREATE INDEX links_created_by_id_idx   ON links (created_by, id DESC);
CREATE INDEX links_team_id_id_idx      ON links (team_id, id DESC);
CREATE INDEX links_team_campaign_idx   ON links (team_id, campaign);
```

- **短碼區分大小寫**：`aB3xYz` 與 `AB3xYz` 是兩條連結。PostgreSQL 預設的排序規則（collation）是區分大小寫的，唯一索引照字元逐一比對；資料庫建立時不要改成不區分大小寫的排序規則。
- **`team_id` 記的是建立當下建立者所屬的團隊**，之後建立者換團隊，連結仍屬於原來的團隊：原團隊的主管繼續管得到，建立者本人依 `created_by` 也還看得到。`admin` 建立的連結沒有團隊。
- **`original_url` 上限 2,048 字元**：瀏覽器與簡訊平台對過長的網址處理不一致，超過時 API 回 `422`、`invalid_url`。
- **沒有記「這條連結屬於哪一次批次建立」的欄位**：目前的 API 與報表都不需要依批次查詢，批次建立的連結靠相同的 `campaign` 與 7 碼的長度辨認。

三個索引對應列表與統計的查詢：

| 查詢 | 用到的索引 |
| --- | --- |
| `marketing` 列出自己的連結，依 `id` 由大到小、從接續標記往後取 | `links_created_by_id_idx` |
| `marketing_lead` 列出團隊的連結 | `links_team_id_id_idx` |
| 依活動名稱統計團隊的點擊數 | `links_team_campaign_idx` |
| 轉址依短碼查詢 | `links_code_key`（唯一約束自帶的索引） |

### click_events

```sql
CREATE TABLE click_events (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  link_id    bigint      NOT NULL REFERENCES links (id),
  clicked_at timestamptz NOT NULL,
  expired    boolean     NOT NULL,
  ip         inet,
  user_agent text,
  referer    text
);
CREATE INDEX click_events_clicked_at_idx ON click_events (clicked_at);
```

- **第一版不分割（partition）**：依時間分割是[開發順序](roadmap.md)〈階段七：優化實驗〉裡的一個實驗，要先量出不分割時刪除過期資料有多慢。分割後主鍵要改成 `(id, clicked_at)`（PostgreSQL 要求分割表的主鍵包含分割欄位，見 [系統設計](system-design.md)〈資料模型〉），改的方式是新建分割表、搬資料、換名，這個 migration 本身就是實驗的一部分，兩套 migration 都要寫。
- **`clicked_at` 由程式給值，沒有 `DEFAULT`**：它是轉址發生的時間，不是寫進資料庫的時間。階段七改成非同步寫入之後，兩者會差幾秒，程式在轉址當下就要記下時間。
- **`expired`**：轉址時連結已到期或已停用、訪客被導到首頁的點擊為 `true`（見 [系統設計](system-design.md)〈到期之後〉）。
- **欄位不設長度約束，由程式截斷**：`user_agent` 與 `referer` 超過 512 字元時截斷再寫入。其他資料表靠約束擋錯誤值；這張表擋下的話，失敗的是一筆點擊紀錄，點擊就少算了。
- `click_events_clicked_at_idx` 給彙總用：排程依時間範圍讀出一天的點擊。

### click_daily

```sql
CREATE TABLE click_daily (
  link_id bigint NOT NULL REFERENCES links (id),
  day     date   NOT NULL,
  clicks  bigint NOT NULL,
  CONSTRAINT click_daily_pkey         PRIMARY KEY (link_id, day),
  CONSTRAINT click_daily_clicks_check CHECK (clicks >= 0)
);
```

- `day` 是 UTC 的日期，與 API 的統計日期相同。
- `clicks` 包含已到期的點擊：行銷要知道舊簡訊還有多少人點，被導到首頁的那些也算在活動成效裡。
- **彙總用重算而不是累加**：排程每次重算今天與昨天的數字，以 `INSERT ... ON CONFLICT (link_id, day) DO UPDATE SET clicks = EXCLUDED.clicks` 寫入。重算的結果與執行幾次無關，Go 與 Laravel 的排程同時跑、或同一個排程重跑，數字都不會重複加。

### refresh_tokens

```sql
CREATE TABLE refresh_tokens (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id    bigint      NOT NULL REFERENCES users (id),
  token_hash bytea       NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL,
  CONSTRAINT refresh_tokens_token_hash_key UNIQUE (token_hash)
);
CREATE INDEX refresh_tokens_user_id_idx ON refresh_tokens (user_id);
```

- `token_hash` 的算法見 [登入與權限](auth-and-roles.md)〈效期與撤銷〉。用 `bytea` 存 SHA-256 的 32 bytes 原始值，不存十六進位字串，兩個後端就不會因為大小寫不同而比對失敗。
- `refresh_tokens_user_id_idx` 給停用帳號與改角色時刪除這個使用者的全部 refresh token。
- 過期的列在換發時發現就刪除；排程清理放在階段六，和點擊彙總一起做。

## 共用的快取與 stream 格式

快取與非同步點擊寫入要到階段七才實作，但兩個後端讀寫同一份資料，格式現在就定下來，到時兩邊照同一份實作。

| 用途 | key | 值 | TTL |
| --- | --- | --- | --- |
| 轉址資料 | `link:{code}` | JSON：`{"link_id": 1, "original_url": "...", "expires_at": "2027-01-04T08:30:00Z", "disabled": false}` | 24 小時；建立時寫入，`PATCH` 時覆寫 |
| 查不到的短碼 | `link_missing:{code}` | `1` | 60 秒；建立連結時刪除 |
| 立即撤銷 | `revoked_user:{使用者 ID}` | 撤銷當下的 Unix 時間（秒） | 15 分鐘，見 [登入與權限](auth-and-roles.md)〈效期與撤銷〉 |

- 快取的值存「判斷要轉到哪裡」需要的資料，不存判斷的結果：到期時間存在快取裡，每次轉址用當下的時間比較，連結在快取的 24 小時內到期也會正確轉到首頁。
- 非同步點擊寫入用 stream `clicks`，consumer group `click_writers`。每筆事件的欄位與 `click_events` 相同：`link_id`、`clicked_at`（RFC 3339、UTC、到毫秒）、`expired`（`1` 或 `0`）、`ip`、`user_agent`、`referer`。

## 程式介面

兩個後端照同一份介面切分程式，介面只放在兩種位置：

- **之後的階段會替換實作的位置**：[開發順序](roadmap.md)〈階段七：優化實驗〉的每個實驗都是換上或包上一個新實作，介面讓實驗只改組裝的那幾行，handler 不動。
- **測試需要控制結果的位置**：亂數與時間。

其餘的程式（handler、驗證、權限範圍）直接寫，不另外抽介面。

| 介面 | 職責 | 階段二的實作 | 之後換上或包上的實作 |
| --- | --- | --- | --- |
| `Resolver` | 依短碼查出轉址需要的資料 | 查 PostgreSQL | 階段七：包在外層的實作（decorator），依序是查快取、查「不存在」的標記、問 Bloom filter |
| `ResolverCache` | 建立與修改連結時同步更新快取 | 什麼都不做 | 階段七：寫入或覆寫 `link:{code}`、刪除 `link_missing:{code}` |
| `ClickRecorder` | 記錄一筆點擊 | 在請求內寫入 `click_events` | 階段七：推進 stream `clicks` |
| `LinkStore` | 連結的建立、查詢、列表、修改 | PostgreSQL | — |
| `UserStore`、`TeamStore`、`RefreshTokenStore` | 使用者、團隊、refresh token 的讀寫 | PostgreSQL（階段四） | — |
| `RevocationStore` | 寫入與查詢立即撤銷 | Valkey（階段四） | — |
| `StatsStore` | 彙總與查詢點擊數 | PostgreSQL（階段六） | — |
| `CodeGenerator` | 產生短碼 | 密碼學安全的亂數 | 測試用：回固定的序列，用來測碰撞重試 |
| `Clock` | 現在的時間 | 系統時間 | 測試用：固定的時間，用來測到期與撤銷 |

### 轉址路徑

轉址是流量最大的路徑，它的介面決定階段七的實驗好不好做，所以這裡寫出 Go 的定義；Laravel 照同樣的方法與欄位定義 PHP interface。

```go
package redirect

// Target 是轉址需要的資料，也是快取 link:{code} 存的內容。
type Target struct {
	LinkID      int64
	OriginalURL string
	ExpiresAt   time.Time
	Disabled    bool
}

// Resolver 依短碼查出轉址需要的資料；短碼不存在時回 ErrNotFound。
type Resolver interface {
	Resolve(ctx context.Context, code string) (Target, error)
}

// Click 對應 click_events 的一列，ClickedAt 是轉址當下的時間。
type Click struct {
	LinkID    int64
	ClickedAt time.Time
	Expired   bool
	IP        netip.Addr
	UserAgent string // 寫入前截斷到 512 字元
	Referer   string // 同上
}

type ClickRecorder interface {
	Record(ctx context.Context, c Click) error
}
```

轉址的 handler 依下面的規則組合這兩個介面：

- `Resolve` 回 `ErrNotFound` 時回 `404`；回其他錯誤時回 `503`。
- 連結已停用、或現在的時間已經到了 `ExpiresAt`，轉到首頁並記 `Expired: true`；否則轉到 `OriginalURL`。
- `HEAD` 請求不呼叫 `Record`。
- **`Record` 失敗時仍然回 `302`**，只寫 log 並遞增點擊寫入失敗的 metric：訪客要的是到達目的地，點擊紀錄寫不進去不能讓轉址失敗。

### 權限範圍

列表、單一連結與統計都依角色限制範圍（見 [API 與路由規格](api.md)〈「範圍依角色」的意思〉）。範圍從 JWT 的 claims 算成一個值，由 `LinkStore` 與 `StatsStore` 放進查詢條件，不在 handler 裡先查再過濾：

| 角色 | 加進查詢的條件 |
| --- | --- |
| `marketing` | `created_by = <使用者 ID>` |
| `marketing_lead` | `team_id = <團隊 ID>` |
| `engineer`、`admin` | 不加條件 |

範圍放在查詢條件裡，範圍外的連結查詢結果就是「沒有這一列」，handler 照「不存在」處理、回 `404`，不會有某個 handler 忘了過濾而回出別的團隊的連結。`engineer` 不看統計是角色的權限，由 handler 在呼叫 `StatsStore` 之前回 `403`。

### 短碼重複的判斷

`LinkStore` 的建立遇到唯一約束衝突時，依被違反的約束名稱判斷：名稱是 `links_code_key` 就回「短碼已被使用」的錯誤，其他約束照一般的資料庫錯誤處理。Go 從 GORM 錯誤裡包著的 pgx 錯誤取得 `ConstraintName`（見〈Go 的資料存取〉），Laravel 從 `QueryException` 的 SQLSTATE `23505` 與錯誤訊息裡的約束名稱取得；這是約束名稱要在 SQL 裡寫明的另一個理由。

拿到「短碼已被使用」之後：

- 自訂短碼：回 `409`、`code_taken`。
- 亂數短碼：用 `CodeGenerator` 重新產生，最多重試 3 次（見 [系統設計](system-design.md)〈產生方式〉）。
- 批次建立：一次 `INSERT ... ON CONFLICT (code) DO NOTHING RETURNING code` 寫入整批，沒有回傳的那幾個短碼在同一個交易裡重新產生、再寫一次，不必整批重來。

## Go 的資料存取

- **用 GORM**（`gorm.io/gorm` 加 `gorm.io/driver/postgres`，底層的驅動是 pgx），和 Laravel 用 Eloquent 對稱：兩個後端都照各自生態系常見的做法寫。這個專案的原則是開發方式照業界慣例，量測是另一個需求，量的就是照慣例寫出來的系統；不為了讓量測乾淨而先改變開發方式。
- **不用 GORM 的 `AutoMigrate`**：schema 由 Atlas 的版本化 migration 管理（見 [infra/postgres](../infra/postgres/README.md)〈誰管 schema〉），model 的 struct tag 只描述欄位與資料表的對應。
- **GORM 在程式碼沒寫出來的地方多做的事**，量測時要知道它們存在：寫入（create、update、delete）預設包在一個交易裡，每次多出 `BEGIN` 與 `COMMIT` 兩次來回；`First` 會在查詢後加上依主鍵排序，依唯一欄位查一筆時用 `Take`。開發時照預設寫；壓測顯示它們是瓶頸時，關掉預設交易（`SkipDefaultTransaction`）或把熱路徑改寫成原始 SQL，就是[開發順序](roadmap.md)〈階段七：優化實驗〉的一個實驗，前後各量一次。
- **短碼重複**：GORM 回傳的錯誤裡包著 pgx 的 `*pgconn.PgError`，用 `errors.As` 取出後讀 `ConstraintName`。GORM 的 `TranslateError` 會把它換成 `gorm.ErrDuplicatedKey`，換完就沒有約束名稱，分不出是短碼還是別的唯一約束，所以不開。
- **批次建立**的 `ON CONFLICT (code) DO NOTHING RETURNING code` 用 GORM 的 `clause.OnConflict{DoNothing: true}` 加 `clause.Returning` 寫出。
- 套件依職責切：`internal/redirect`（轉址的 handler 與上面的介面）、`internal/link`、`internal/auth`、`internal/stats`，PostgreSQL 與 Valkey 的實作放在 `internal/store/postgres`、`internal/store/valkey`。
- 每張表一個 struct，可以是空值的欄位用指標（`*int64`、`*time.Time`），例如 `Link.TeamID`、`Link.DisabledAt`。

## Laravel 的 model

| model | 資料表 | 要另外設定的地方 |
| --- | --- | --- |
| `Team` | `teams` | `const UPDATED_AT = null;` |
| `User` | `users` | `const UPDATED_AT = null;`；隱藏 `password_hash`；改寫 `getAuthPassword()` 回傳 `password_hash`。不再需要 `Notifiable`、`remember_token` 與 `email_verified_at` |
| `Link` | `links` | `const UPDATED_AT = null;`；`getRouteKeyName()` 回 `code`，路由參數直接用短碼；`expires_at`、`disabled_at` cast 成 `datetime` |
| `ClickEvent` | `click_events` | `public $timestamps = false;`，`clicked_at` 由程式給值 |
| `ClickDaily` | `click_daily` | 指定 `$table`（Laravel 預設會找複數的 `click_dailies`）；主鍵是兩個欄位，Eloquent 不支援複合主鍵，所以只用它讀，寫入的重算用查詢建構器（query builder）的 `upsert` |
| `RefreshToken` | `refresh_tokens` | `const UPDATED_AT = null;` |

- **API 回應用 API Resource 組，不用 model 的 `toJson()`**：model 預設序列化出來的時間帶小數秒與 `+00:00`，欄位名稱也是資料表的名稱（例如 `disabled_at`），而 API 要的是到秒的 `Z` 結尾時間與 `disabled` 布林值（見 [API 與路由規格](api.md)〈連結物件〉）。
- 介面放在 `app/Contracts/`，實作放在 `app/Services/`，在 `AppServiceProvider` 綁定；階段七換實作時只改綁定。
- Laravel 預設的 `create_users_table` 刪掉，`cache` 與 `jobs` 兩張表的處理見 [infra/postgres](../infra/postgres/README.md)〈業務表由這兩套 migration 自己定義〉。

## 資料表與 API 欄位的對應

API 回應的欄位不是資料表欄位的直接輸出，兩個後端照下表轉換：

| API 欄位 | 來源 |
| --- | --- |
| 連結的 `code` | `links.code`；`links.id` 不對外 |
| `short_url` | `SHORT_DOMAIN` 加 `code` |
| `disabled` | `links.disabled_at IS NOT NULL` |
| `created_by` | `links.created_by` 對應的 `users.id` 與 `users.email` |
| `clicks_total` | `click_daily.clicks` 的加總；階段六之前沒有彙總，回 `0` |
| 使用者的 `team` | `users.team_id` 對應的團隊，沒有團隊時是 `null` |
| 分頁的 `next_cursor` | 這一頁最後一筆的 `id`，轉成十進位字串 |
