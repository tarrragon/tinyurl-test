# CI 設計

這份文件說明 CI 在這個 monorepo 裡怎麼決定要跑哪些 job、哪些 job 擋合併，以及什麼情況下才考慮把 repo 拆開。CI 用 GitHub Actions，workflow 在[開發順序](roadmap.md)的〈階段一：定案與骨架〉建立。

## 為什麼全部放在同一個 repo

這個專案最常見的修改會同時動到好幾個元件：改一個 API 欄位，要一起改 Go、Laravel、契約測試、前端，可能還有 migration。放在同一個 repo 裡，這是一個 commit、一次 CI，契約測試在同一個版本上驗兩個後端。每個元件各開一個 repo 的話，同一個修改要拆成多個 PR，還要另外記下哪幾個版本才搭得起來。

「只改前端時不要連後端一起建」這個需求，用路徑過濾就能做到，不需要拆 repo。

## 依改動的路徑決定要跑的 job

每個應用元件的 Docker build context 就是它自己的目錄（見 `docker-compose.yml`），所以一個目錄的改動只會影響那個元件的映像檔。workflow 先用路徑過濾（例如 `dorny/paths-filter`）判斷這次改了哪些目錄，再只啟動對應的 job：

| 改動的路徑 | 要跑的 job |
| --- | --- |
| `services/go/**` | Go 的 lint、單元測試、建映像檔，以及整合測試 |
| `services/laravel/**` | Laravel 的 lint、單元測試、建映像檔，以及整合測試 |
| `web/portal/**` | 前台的 lint、型別檢查、建置 |
| `web/admin/**` | 後台的 lint、型別檢查、建置 |
| `infra/nginx/**` | Nginx 設定檢查（`nginx -t`），以及整合測試 |
| 只改 `*.md` | 不跑 job |

### 改了就全部重跑的共用路徑

下面這些檔案被多個元件依賴，改了它們卻只跑單一元件的 job，會讓壞掉的組合通過 CI。所以它們列在「全部重跑」的觸發清單裡：

- 契約測試的目錄（位置在階段一決定）
- migration 的目錄：兩個後端讀同一份 schema，不論 migration 由哪一邊的工具管理
- `docker-compose.yml`、`.env.example`
- `docs/` 底下的 API 規格（錯誤格式、錯誤碼、分頁格式）
- `.github/workflows/**`：workflow 本身改了，要確認每個 job 都還跑得起來

之後新增被多個元件依賴的檔案時，例如從 API 規格產生的程式碼，同時把它加進這份清單。漏加不會有任何錯誤訊息，只會讓 CI 在該跑的時候沒跑。

## 整合測試

整合測試用 `docker compose up` 起完整環境，對每個已經實作的後端各跑一次契約測試，並在回應的 `X-Backend` header 確認請求確實打到那個後端。Go 與 Laravel 在同一個 upstream 裡行為一致，只有這個 job 驗得到，各元件的單元測試驗不到。

整合測試什麼時候開始擋合併，跟著開發順序走：

| 階段 | 整合測試的狀態 |
| --- | --- |
| 階段一 | 會跑、不擋合併：此時還沒有任何實作，契約測試全部失敗是預期的 |
| 階段二起 | Go 的契約測試擋合併 |
| 階段五起 | Laravel 的契約測試也擋合併 |

## 不放進 CI 的項目

壓測不在 CI 裡跑。CI 的執行機器規格不固定，而且會和其他工作共用資源，量出來的數字無法跟之前的結果比較。壓測照 [loadtest](../loadtest/README.md) 在固定規格的機器上手動執行，結果記錄機器規格與容器資源上限。

## 什麼情況下考慮拆成多個 repo

下列條件出現時，才重新評估要不要拆 repo。目前一項都不成立：

- **存取權限要分開**：例如某個團隊只能看前端程式碼。git 的權限單位是整個 repo，沒辦法只開放某個目錄。
- **某個元件要發佈給外部使用**：例如做成 SDK 套件，它的版本節奏由外部使用者決定，跟服務端的部署無關。
- **repo 的大小拖慢日常操作**：clone、checkout 或 CI 的 checkout 步驟慢到影響工作。

元件數量增加到路徑過濾難以維護時，先考慮從依賴關係自動計算受影響範圍的建置工具（例如 Nx、Turborepo、Bazel），再考慮拆 repo。
