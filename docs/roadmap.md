# 開發順序

這個 monorepo 是練習專案，[系統設計](system-design.md) 裡的每一項設計最後都會實作。這份文件排的是**先後順序**，排法依三個原則：

1. **改了會牽動多方的決定先定**：短碼格式、網域、API 錯誤格式、JWT 格式、metrics 名稱，一旦兩個後端與前端都依賴它們，改動就要三邊同時改。這些在第一個階段就定下來，實作可以排在後面。
2. **量測先於優化**：快取、非同步寫入、Bloom filter 這些設計，先用最簡單的做法上線、用壓測量出瓶頸，再加上設計、用同一個情境重量一次。每個優化都是一次有前後對照的實驗，看得到它解決了多少問題。
3. **一個後端做通再做第二個**：Go 版先做出可用的參考實作與契約測試，Laravel 版照同一套契約測試對齊，避免兩邊各自長出不同的行為。

每個階段寫明目標、範圍、完成條件與它依賴哪些前面的階段。完成條件是可以驗證的狀態，不是「寫完了」。

## 階段一：定案與骨架

**目標**：把之後改了會牽動多方的決定定下來，讓本機環境起得來。

- API 規格：路由、端點、錯誤格式（RFC 9457）與錯誤碼清單、分頁格式、`X-Backend` 回應 header，已寫在 [API 與路由規格](api.md)。Go 與 Laravel 共用同一個 upstream，同一個錯誤兩邊回的格式必須一樣。
- 資料表、共用的快取 key 與程式介面已定在 [資料表與程式介面](data-model.md)。兩個後端照它各寫第一版 migration（Laravel 用自己的 migration，Go 用 Atlas），同一個資料庫由 `SCHEMA_OWNER` 指定的那一套執行；刪掉 Laravel 預設的 `create_users_table`。做法見 [infra/postgres](../infra/postgres/README.md)〈誰管 schema〉。
- 定 metrics 的名稱與標籤（請求數、延遲、錯誤、快取命中），兩個後端之後照同一份名稱輸出，才能並排比較。
- 建立契約測試的位置與工具：一組與語言無關、對 HTTP API 發請求並檢查回應的測試，兩個後端都要通過。
- `docker compose up` 起得來 PostgreSQL、Valkey、Nginx。
- 每個服務有 healthcheck，Gatus 監看各服務、`scripts/health.sh` 供 SSH 查詢（見 [infra/monitoring](../infra/monitoring/README.md)）。
- 建立 CI 的 workflow：依改動的路徑只跑對應元件的 job，共用路徑（契約測試、兩個後端的 migration、API 規格、`docker-compose.yml`）改了就全部重跑，整合測試起完整環境跑契約測試，另有一個 job 比對兩套 migration 建出的 schema。設計見 [CI 設計](ci.md)。

**完成條件**：API 規格、錯誤格式、metrics 名稱寫進文件；兩套 migration 都能在空資料庫上建出全部業務表，且 CI 比對兩套建出的 schema 相同；契約測試能跑（此時全部失敗是正常的）；CI 對每個 PR 依改動的路徑啟動對應的 job，整合測試會跑但還不擋合併。

## 階段二：核心路徑的最小實作（Go）

**目標**：用最簡單的做法讓建立連結與轉址能用，作為之後所有優化的對照組。

- Go 版實作 `POST /api/links` 與 `GET /{code}`：亂數產生短碼、唯一索引擋重複、到期轉首頁。
- 轉址直接查 PostgreSQL，**不加快取**；點擊事件在請求內**同步寫入** `click_events`。這兩個簡化是刻意的，之後的階段要量出它們的上限。
- 每次記錄點擊時產生點擊識別碼（UUIDv7），寫進 `click_events.click_id`，目標網址在 `CONVERSION_HOSTS` 裡時附上 `tc` 參數。這是與電商之間的契約，從第一版的轉址就帶著，轉換回報到階段七才實作（見 [系統設計](system-design.md)〈點擊識別碼與轉換回報〉）。
- 健康檢查 `/-/healthz`，回應帶 `X-Backend: go`。
- Nginx 依 `SHORT_DOMAIN`、`APP_DOMAIN` 分流到 Go。

**依賴**：階段一。
**完成條件**：契約測試裡建立連結與轉址的部分全部通過；CI 的整合測試開始以 Go 的契約測試擋合併。

## 階段三：觀測與第一次壓測基準

**目標**：在加任何優化之前，先量出最簡單做法的能力，並建立之後每個階段都會用到的量測工具。

- 新增 `infra/observability/`：指標收集（例如 Prometheus）與面板（例如 Grafana）加入 compose，Gatus 開啟 `metrics` 讓 Prometheus 收集探測結果；Nginx access log 與後端的結構化 log 照 [API 與路由規格](api.md)〈請求 log〉的欄位送進 log 系統，工程師在 Grafana 查逐筆請求；Go 版提供 `/-/metrics`（放在 `/-/` 下的理由見 [系統設計](system-design.md)〈健康檢查〉），輸出結構化 log。
- 照 [loadtest](../loadtest/README.md) 寫出轉址基準與短碼掃描兩個情境的腳本，以及產生測試資料的腳本。
- 跑第一次壓測，記錄可承受的流量、先到極限的那一層、PostgreSQL 的連線數與查詢延遲、點擊數比對。

**依賴**：階段二。
**完成條件**：`loadtest/results/` 有第一份基準紀錄，附機器規格與容器資源上限。

## 階段四：登入、權限與前台

**目標**：讓行銷團隊能登入並建立連結。

- Go 版實作 JWT 登入、refresh token、以使用者為單位的立即撤銷與角色檢查（見 [登入與權限](auth-and-roles.md)）。
- `web/portal` 用 Vue 3 + Vite 建出前台：登入、建立連結、列出自己的連結。
- 契約測試補上登入與權限的部分。

**依賴**：階段二（API 與 Nginx 分流）。
**完成條件**：前台能完成「登入 → 建立連結 → 用短網址轉址」整條流程；不同角色看到的連結範圍符合權限表。

## 階段五：Laravel 版對齊

**目標**：讓第二個實作通過同一套契約，並在同一個 upstream 輪流接請求。

- Laravel 版實作階段二與階段四的全部 API，回應帶 `X-Backend: laravel`，輸出同一份名稱的 metrics。
- 共用 JWT 金鑰、快取 key 格式與錯誤格式（見 [services/laravel](../services/laravel/README.md)〈與 Go 版要對齊的地方〉）。
- Nginx 把 Go 與 Laravel 放進同一個 upstream。

**依賴**：階段四。
**完成條件**：契約測試對兩個後端各跑一次全部通過，CI 的整合測試也以 Laravel 的契約測試擋合併；兩個後端同時在線時，前台操作的結果與只有其中一個時相同。用轉址基準情境分別量兩個後端，各記一份結果。

## 階段六：後台與點擊統計

**目標**：讓行銷看得到活動成效、工程師看得到系統狀態。

- 排程把 `click_events` 彙總到 `click_daily`；兩個後端實作統計 API。
- `web/admin` 建出後台：行銷看依管道、活動、時間的點擊數；工程師看請求 log 與錯誤率；管理者管理使用者與角色。

**依賴**：階段三（結構化 log 與 metrics）、階段五。
**完成條件**：壓測送出的轉址次數與後台記到的點擊數一致。

## 階段七：行銷分析

**目標**：讓行銷回答三類問題：特定客群對一次發送的反應、廣告與簡訊帶來多少購買、收到通知的客人有沒有回來。設計見 [系統設計](system-design.md)〈行銷分析：收件人對應、點擊識別碼與轉換回報〉。

- 資料表在階段一的 migration 就已建好（`sends`、`link_recipients`、`conversions`、`api_keys`、`campaign_daily`、`recipient_daily`、`analytics_watermarks`），這個階段只寫程式。
- `POST /api/sends` 收收件人清單（`recipient_ref` 與客群標籤），寫入 `sends` 與 `link_recipients`；`GET /api/sends`；個資刪除的 `POST /api/recipients/erase`。
- 伺服器金鑰（`api_keys`）與 `POST /api/conversions`；後台的金鑰管理頁。
- 點擊分類規則放進兩個後端共用的設定檔；排程依 [資料表與程式介面](data-model.md)〈分析彙總的重算〉重算 `campaign_daily` 與 `recipient_daily`（advisory lock、水位、歸因期間）。
- 統計 API 加上客群與轉換；每位收件人結果的 CSV 匯出；後台的活動頁顯示客群比較與轉換。
- 契約測試涵蓋：轉換重送回 `200` 不重複計算、內容不同回 `409`；別的團隊的金鑰回報的轉換不進報表；清除收件人對應並重算後，匯出檔裡沒有那位客人而活動與客群的數字不變；兩個後端對同一批點擊與轉換重算出一樣的彙總；`marketing` 看到的活動統計只含自己建立的連結。

**依賴**：階段六。
**完成條件**：壓測的混合流量情境加上模擬電商回報轉換的請求，後台的轉換數與送出的回報數一致（扣掉刻意送出的重送與對不到點擊的回報）；兩個後端在線時的彙總結果與只有其中一個時相同。

## 階段八：優化實驗

**目標**：每次加一個設計，用壓測量出它解決了多少問題。每個實驗都照同一個格式記錄：要解決的現象（從前面的壓測結果找）、加上的設計、用哪個情境量、前後的數字。

建議順序由「最可能先遇到的瓶頸」排起，實際順序依階段三與階段五的壓測結果調整：

| 實驗 | 要解決的現象 | 量測的情境 |
| --- | --- | --- |
| 轉址快取（Valkey，建立時同時寫入） | 轉址每次都查 PostgreSQL，連線數與延遲隨流量上升 | 轉址基準、爆紅連結 |
| Nginx 限流 | 單一來源能打滿服務 | 限流驗證 |
| 快取「不存在」的結果 | 錯誤短碼重複打到資料庫 | 短碼掃描 |
| 非同步點擊寫入（stream＋背景程序＋consumer group，Valkey 開 AOF；寫入用 `ON CONFLICT (click_id) DO NOTHING`） | 尖峰時同步寫入拉高轉址延遲、佔滿連線 | 轉址基準、長時間穩定、點擊數比對（含停掉一個消費者、讓訊息重新投遞的情形） |
| Bloom filter | 隨機掃描的短碼每次都不同，快取「不存在」擋不住 | 短碼掃描 |
| `click_events` 依時間分割（`click_id` 的唯一索引改成 `(click_id, clicked_at)`，轉換對應點擊改用點擊識別碼加時間範圍查詢） | 刪除過期資料變慢、索引變大 | 長時間穩定；分割前後各量一次彙總重算的耗時 |
| 關掉 ORM 的預設交易、熱路徑改寫原始 SQL | 轉址與點擊寫入的每個請求，ORM 多送出的 SQL 與來回拉高延遲（GORM 的預設交易、Eloquent 建立 model 物件） | 轉址基準 |
| 統計查詢讀 PostgreSQL 唯讀副本（依用途分流，其餘查詢照舊讀主庫；Go 用 dbresolver 的具名 resolver、Laravel 用另一個只連副本的資料庫連線） | 後台統計查詢與轉址同時跑時，轉址的 p99 升高、主庫的連線數或 CPU 有一部分花在統計查詢上 | 混合流量 |
| 快取伺服器比較（Valkey、Dragonfly） | 比較兩者在同一條件下的差異 | 轉址基準、爆紅連結 |

每個實驗完成時，把 [系統設計](system-design.md) 裡對應那一段的狀態從「規劃」改成「已實作」，並連到那次的壓測紀錄。

## 練習環境跳過的項目

這個專案不是上線服務，以下項目刻意不做。若之後要轉成正式服務，從這份清單重新逐項判斷：

- TLS 憑證與 HTTPS（本機用 `*.localhost`）
- 資料庫備份、還原與演練
- 秘密管理（目前用 `.env`）
- 高可用：多個 PostgreSQL 與 Valkey 節點、多區域
- 個人資料的保留期限與存取稽核（收件人對應的刪除請求在階段七提供，因為對應表與點擊事件分開存放，刪除只動一張表）
- 告警與值班
- 對外的狀態頁（觸發條件與設計見 [系統設計](system-design.md)〈健康檢查〉的〈對外的狀態頁〉）

## 前端的版本相容

瀏覽器可能還開著舊版的前端頁面，而後端已經部署新版。API 的修改只做新增、不改既有欄位的語意，舊頁面就不會壞；要改語意時，照 [系統設計](system-design.md) 的錯誤格式與欄位規則另開新的欄位或端點。
